# Physical provider capacity

Physical calls have durable occupancy separate from Run execution slots and environment allocations. The deployment defaults are null caps: occupancy is counted, but there is no physical concurrency ceiling. Hard evaluation preflight requires an active policy with positive global, original-requester, and provider caps. There are no built-in numerical physical limits. Existing monthly monetary checks and user/team concurrent-task limits keep their separate semantics.

The private activation service and operator CLI are available. Kernel startup initializes the policy before workers start; API startup reads it without operator privileges and rejects a configured mismatch. An absent initial policy is permitted for API bootstrap, but physical sends require an active matching policy. Ordinary and evaluation model.call invoke/stream and adapter retries use the durable guard. Direct probes, embedding batches and image transports use the same physical pools. Accepted tool, retrieval and knowledge-build activities retain their actual Run/claim and F07 receipts for auxiliary model sends. Unsupported evaluation auxiliary sends fail closed; recorded replay and governed isolated retrieval do not fall through to ordinary providers. `initialize_physical_policy` bootstraps revision 1 only and requires an exact active-policy match on restart. Settings are `PHYSICAL_BUDGET_POLICY_REVISION`, `PHYSICAL_GLOBAL_CONCURRENCY`, `PHYSICAL_USER_CONCURRENCY`, and `PHYSICAL_PROVIDER_CONCURRENCY`. Omit optional environment values for null caps.

Using the existing kernel deployment credentials, from `api`:

```sh
python -m scripts.physical_budget_policy --policy /absolute/path/physical-policy.json --expected-revision 1
```

The JSON must contain revision 2 and the desired complete policy. Expected revision 0 permits initial revision 1 bootstrap; exact repeated activation is idempotent. The example file intentionally represents the uncapped default, not a recommended evaluation capacity. Operators must choose positive limits for their deployment before enabling hard evaluation. Coordinate activation with worker configuration and restart; old workers cannot reinstall an old policy or admit under stale limits. API callers can read active limits but cannot activate policy or inspect global counters.

Activation preserves occupied slots and all reserved/spent budgets. Lowering a cap below occupancy blocks new sends without releasing existing requests. Null removes enforcement while retaining occupancy. Settlements of older reservations remain valid after policy changes. Neither expiry nor restart clears unknown remote effects.

E06 initial admission creates C1 namespace/source/budget bindings, then `evaluation_execution.prepare`, then enqueues Run creation in the same caller transaction. Preparation creates a unique immutable initial work-unit lineage. For infrastructure replacement, create the new C1 source/budget binding and call `evaluation_lineage.link_replacement(scope, new_run_id, predecessor_run_id=..., expected_generation=...)` before execution preparation and enqueue, all in that transaction. Namespace locking serializes lineage creation and closure. The hook requires the same namespace, case, subject and selected configuration, repetition, purpose, requester and policy proof, and a released accepted failed/retry-wait predecessor with no unknown activity/physical effect. E06 must additionally establish retry eligibility from its actual CaseResult evidence. A second same-unit root cannot omit its predecessor; a linked predecessor cannot resume new work. Cancellation remains possible. Replacement uses the original root's model-round counters, including all fallback and infrastructure retries, with a maximum of three physical sends per evaluation logical round.

The restricted model-judge protocol permits original round 0 and repair rounds 1–2 as distinct planned model Activities within the same bound judge Run. Each repair requires the accepted prior `judge_status=invalid` result, its decision digest and persisted Activity payload; retry-generation or arbitrary Run/Activity/nonce changes cannot supply repair authority. The current batch scheduler and judge service own admission; this physical-capacity hook does not expose a public bypass.

Final response evidence releases physical occupancy even if token or monetary categories remain unknown. Those incomplete billing holds remain conservative. Timeout/cancel/crash without conclusive response evidence retains both occupancy and billing holds. F07 final usage facts remain immutable: complete late usage before any final fact can settle once, an exact duplicate is idempotent, and changed evidence after a partial final fact is rejected. Adapters finalize only after actual response/stream completion, never on early usage chunks. Verified native explicit rejection responses release physical occupancy with unknown billing; timeouts, ambiguous conflicts, server failures, and unregistered gateway errors retain occupancy and billing holds. SDK internal retries are disabled; resilience and adapter retries obtain a new committed receipt for every send.

Ordinary new user admission stores a private HMAC requester envelope in its immutable F07 admission snapshot, bound to the Run and scope and verified against the actual signed DB admission authorization. Each new send rechecks current user/token/team membership. The first DB physical-policy activation establishes the historical cutoff: missing proof after cutoff fails closed. Verified personal historical work uses its persisted owner; historical team work shares an explicit `legacy_unknown_requester` aggregate bucket. Historical team work cannot claim per-original-user enforcement. Trusted system admission records its explicit actor. Evaluation always uses its C1 original requester. Proofs never enter public view DTOs.

Both ordinary and evaluation calls acquire a canonical provider-kind bucket and an inventory-declared account bucket. Unmapped ordinary endpoints share one unknown-account bucket. The same configured provider cap applies to both: independent accounts of one provider kind share the conservative kind ceiling. Account identity is a typed SHA-256 key, preventing strings such as `unknown` from colliding with the unmapped bucket. These identities express trusted deployment metadata, not discovery of an underlying gateway account. Versioned activation changes both limits without clearing either count.

Direct API calls have their own immutable signed request receipt, never a fabricated Run or claim. The receipt records original scope/requester, purpose, configured and wire model, endpoint/provider and a payload digest. Each real batch/retry commits a fresh reservation before network I/O; cache/blank/empty embedding work sends nothing. API uses only the existing narrow signed operation, with no global counter read or kernel credentials. New sends validate active deployment policy and current user/token/team after blocking capacity locks. A separate domain-separated completion signature can settle only the exact original direct receipt after requester revocation; it cannot reserve, replace identity/demand, or cross scope. Provider-reported token evidence is retained when available; direct monetary amounts remain unknown, especially image requests whose wire model differs from the configured chat model. Ambiguous errors/cancellation retain occupancy.

Request/build clients and resilience fallback clients are closed on completion and failure. Memory embedding runs outside business transactions; writes recheck scoped entry/session visibility, and updates compare the original revision under a row lock to avoid overwriting changes made during embedding. This works with a one-connection API pool without committing the caller transaction implicitly.

Subject and model-judge Runs bind distinct published configurations/purposes to the same immutable namespace. Both add to its `5:batch` Token/money total; their F07 configurations, dispatch facts and `6:purpose` counters remain separate. A judge can exhaust the remaining shared budget and prevent the next subject transport. Caller purpose or policy hints cannot replace the bound published authority. E06 materialization must use the trusted kernel caller UoW when also allocating E04 environments, carrying the verified original requester separately; API 202 enqueue does not allocate environments directly.
